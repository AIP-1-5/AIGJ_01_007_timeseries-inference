# 과제 7에서 배운 것: 엣지 최적화

결과: [docs/reports/007-edge](../reports/007-edge/README.md) · 코드: `tsmodel/edge.py`

## 무엇을 했나

과제 3·4·5 모델 세 개를 ONNX로 바꿨다. PyTorch CPU, PyTorch GPU, ONNX Runtime CPU로 지연(평균·p95)과 변환 후 차이를 쟀다. 변환 후 차이는 CO₂ 0.0003ppm, 분류 바뀐 비율 0%로 기준을 통과했다. TensorRT FP16은 API가 바뀌어 1차에 실패했다. 2차에는 보드 메모리가 가득 차 재부팅됐고, 측정하지 못했다.

## 개념 → 왜 필요한가

| 개념 | 비유 | 정의 | 왜 필요한가 | 백엔드로 치면 |
|---|---|---|---|---|
| ONNX | PDF (어느 프로그램에서나 열림) | 모델 구조와 가중치를 담는 공용 파일 형식 | 학습한 곳(맥)과 실행할 곳(보드)이 달라도 같은 모델을 쓴다 | OpenAPI 스펙, JSON 직렬화 |
| ONNX Runtime | PDF 뷰어 | ONNX를 빠르게 실행하는 엔진 | PyTorch보다 호출 비용이 훨씬 작다(이번에 400배) | JIT 없이 미리 컴파일된 바이너리 |
| TensorRT | 그 보드 전용으로 맞춘 기계 | NVIDIA GPU용 최적화 엔진. 보드에서 직접 빌드 | GPU에서 가장 빠르다. 빌드한 GPU·버전에 묶인다 | 특정 CPU용으로 컴파일한 네이티브 바이너리 |
| FP16 | 소수점 아래를 반만 적기 | 숫자를 16비트로 저장 | 메모리 절반, GPU에서 빠름. 대신 오차가 생길 수 있어 변환 후 차이를 잰다 | 정밀도를 낮춘 캐시 |
| 워밍업 | 차 시동 걸고 잠깐 기다리기 | 처음 몇 번은 측정에서 뺀다 | 첫 실행은 메모리 할당·준비 때문에 느리다 | JVM 워밍업 뒤 부하 테스트 |
| p95 | 느린 쪽 5% 경계 | 100번 중 95번은 이보다 빠름 | 매분 마감이 있는 서비스는 가끔 느린 한 번이 문제다 | API SLA p95/p99 |

## 알아둘 결과

- 작은 모델에서는 **계산량보다 프레임워크 호출 비용**이 지연을 정한다. PyTorch CPU 53ms, ONNX Runtime CPU 0.12ms.
- GPU가 CPU(ONNX Runtime)보다 느렸다. 데이터를 GPU로 옮기는 비용이 계산보다 크다. "GPU = 항상 빠름"이 아니다.
- **측정 중 CPU 사용률이 70~97%였다.** 다른 작업과 같이 돌아서 CPU 숫자는 실제보다 클 수 있다. 측정은 혼자 돌 때 해야 한다.

## 짚어 둘 것 (동시성·병목)

- 보드 메모리 8GB는 CPU와 GPU가 같이 쓴다. TensorRT 빌드는 작업 메모리를 크게 잡는다. 상한(256MB)을 걸고, 남은 메모리가 3GB보다 적으면 시작하지 않게 했다. 커넥션 풀 최대 개수를 정해 DB를 지키는 것과 같다.
- 공간이 늘면 지연은 공간 수 × 모델 수로 늘어난다. 지금 0.1ms대라 수백 공간도 여유가 있다(추정).

## 말로 설명할 수 있어야 할 것 3개

1. 변환 후 "같은 결과"를 무엇으로 확인했는지(CO₂ ppm 최대 차이, 분류 바뀐 비율).
2. ONNX Runtime이 PyTorch보다 400배 빠른 이유.
3. 보드가 왜 재부팅됐고, 다시 잴 때 무엇을 바꿨는지.
