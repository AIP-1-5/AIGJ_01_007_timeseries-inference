# 학습 노트: 과제 1 spec (데이터 수집 체계)

날짜: 2026-10-21 · 문서: [spec.md](../../specs/001-data-collection/spec.md)

## 처음 나온 용어

| 용어 | 비유 | 쉬운 정의 | 백엔드 대응 |
|---|---|---|---|
| MQTT | 단톡방. 주제(방)를 구독하면 그 방에 올라온 글이 나에게 온다 | 가벼운 발행/구독 메시지 프로토콜 | Kafka·RabbitMQ의 topic 구독 |
| 브로커(broker) | 단톡방 서버 | 메시지를 받아 구독자에게 나눠 주는 서버(교육장 공용 브로커, 주소는 `.env`) | 메시지 큐 서버 |
| 토픽(topic) | 방 이름. `+`는 "아무 글자 한 칸" | `application/+/device/+/event/up` 같은 경로 문자열 | Kafka topic, URL 패턴 |
| 업링크(uplink) | 센서가 보낸 편지 | 센서 → 서버 방향 메시지. 측정값이 `object`에 들어 있다 | 클라이언트 요청 본문 |
| LoRaWAN / ChirpStack | 저전력 무전기 / 무전 교환국 | 센서 무선 규격 / 그 메시지를 모아 MQTT로 내보내는 서버 | API 게이트웨이 |
| 게이트웨이 | 무전 중계탑 | 센서 전파를 받아 서버로 넘기는 장비. 자기 시계가 틀릴 수 있다 | 로드밸런서·프록시 |
| fCnt | 편지 일련번호 | 센서가 보낼 때마다 1씩 올리는 번호. 건너뛰면 편지를 잃은 것 | 시퀀스 번호, Kafka offset |
| 재가입(join) | 번호표를 새로 뽑음 | 센서가 네트워크에 다시 붙는 것. fCnt가 0부터 다시 센다 | 시퀀스 리셋 |
| 커버율 | 출석부에서 출석 칸 비율 | 1분 칸마다 값이 하나라도 있으면 채워진 칸. 채운 칸 ÷ 전체 칸 | 가용성(uptime) 비율 |
| 확인 기준(AC) | 시험 채점표 | 과제가 "완료"인지 판정하는 조건. 원문 그대로 옮긴다 | 인수 테스트 조건 |

## 무엇을 했나

- 과제 1 확인 기준 3개(AC-1 브로커 재시작 1분 내 복구, AC-2 재부팅 자동 시작, AC-3 24시간 커버율 95%)와 산출물 2개(D-1 현황 보고, D-2 형식 변경 기록)를 spec 완료 조건으로 그대로 옮겼다.
- 사용자 스토리 4개로 나눴다: US1 저장, US2 장애 복구, US3 현황 보기, US4 설정으로 대응.
- 실제 메시지 30건을 보고 발견한 함정을 Edge Cases에 적었다: 게이트웨이 시계 5분 오차, 중복 메시지, fCnt 감소, 태그 누락, 긴 전송 간격 센서.

## 왜 이렇게 했나

- 채점이 확인 기준 충족 여부라서, 기준 문장을 바꾸면 "무엇을 통과했는지"가 흐려진다. 그래서 원문을 그대로 두고 측정 방법(SC-001~007)만 구체화했다.
- 데이터를 먼저 보고 spec을 썼다. 시계 오차나 중복은 문서만 봐서는 몰랐다. 이걸 놓치면 1분 칸이 어긋나거나 건수가 부풀어 커버율이 틀린다.
- 회의실 센서(약 10분 간격)는 1분 커버율이 구조적으로 10%라 판정 방식을 내가 정하지 않고 강사 확인(10/22)으로 미뤘다. 범위 해석은 내가 정할 일이 아니다.

## 말로 설명할 수 있어야 할 것 3개

1. 측정 시각을 왜 메시지의 `time`이 아니라 `nsTime`으로 잡는가 (게이트웨이 시계가 5분 빠름).
2. 중복을 왜 `deduplicationId`가 아니라 "센서 + 일련번호"로 판단하는가 (같은 메시지 두 건의 deduplicationId가 서로 다름).
3. 결측이 생겼을 때 "센서·무선 손실"과 "수집기 손실"을 fCnt로 어떻게 구분하는가 (번호가 건너뛰었나, 이어지는데 우리가 없나).

## 스스로 확인할 질문 2개

1. 브로커가 끊긴 동안 온 메시지를 잃었다면, 현황 보고에서 그 구간은 어떤 원인으로 분류되는가?
2. 센서가 재가입해서 fCnt가 0부터 다시 오면, 기본키 `(device_id, f_cnt, item)`만 쓸 때 무슨 일이 생기는가?
