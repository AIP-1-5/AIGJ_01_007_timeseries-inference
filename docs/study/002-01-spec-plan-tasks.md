# 학습 노트: 과제 2 spec → plan → tasks → 구현

날짜: 2026-10-21 · 문서: `specs/002-data-baseline/` · 코드: `tsdata/`, `config/prep.toml` · 사용자 지시로 계획 승인과 구현을 한 번에 진행

## 무엇을 했나

- **spec**: 확인 기준 3개(정규화는 학습 기간만, 같은 시점·같은 조건, 최강 기준선과 이유)와 산출물 2개(진단서, 성능표)를 원문 그대로 옮겼다. 데이터 사실(오류값 0·65535·−0.1·127.5, 다른 이름의 공간)은 Edge Cases에 숫자로 적었다.
- **research/plan**: 스냅샷 고정, 정제 범위, 5분·중앙값, 결측 채움, 기간 분할, 평가 시점, 일정 추정을 R1~R8로 결정.
- **tasks**: 17개. 테스트를 같은 단계 구현보다 먼저.
- **구현**: `tsdata/influx.py`(스냅샷), `prep.py`(공용 전처리), `baselines.py`, `diagnose.py`, `python -m tsdata all`. 테스트 17개 추가(전체 108개).

## 왜 이렇게 했나

- **스냅샷부터**: InfluxDB는 계속 쌓이므로 같은 질의도 내일 다른 답을 준다. 결과를 다시 만들 수 있어야 해석을 믿을 수 있다(원칙 IV).
- **전처리를 한 파일로**: 과제 3~8의 학습·서비스가 같은 함수를 부른다. 복사하면 조용히 갈라진다(원칙 III).
- **구현 중 계획 두 개를 고쳤다**(R4 결측, R7 평가 시점). 실데이터 숫자가 이상해서 알아챘다. 고친 이유는 research.md와 decisions.md에 남겼다.

## 짚어 둘 것

- **누수 점검 위치**: 기간 분할(시간순), 정규화(학습 관측 칸만), 결측 채움(과거 값만), 기준선 입력(t 이전 값만, 어제 값 = t+h−24h ≤ t), 일정 추정(학습 기간 곡선만).
- **데이터가 늘면**: 원본을 한 번에 메모리에 올린다(3.5GB). 항목별 처리로 나눌 수 있게 함수가 항목을 구분한다.

## 말로 설명할 수 있어야 할 것 3개

1. spec에 "5분·중앙값" 같은 구현 방식을 쓰지 않고 research에 둔 이유(무엇 vs 어떻게).
2. 평가 시점 파일이 왜 과제 3의 공정성을 지키는 장치인지.
3. 일정 자료 없이 일정 분석을 한 방법과 그 한계(일정을 CO₂로 추정했으므로 "반응 시간"은 평소 대비로만 의미가 있다).
