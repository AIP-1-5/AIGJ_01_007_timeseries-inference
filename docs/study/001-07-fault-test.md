# 001-07 브로커 장애 시험 (T029, 2026-10-23)

## 무엇을 했나

- 시험 4회를 `deploy/fault-test-t029.sh` 한 번 실행으로 묶었다. sudo 비밀번호는 한 번만 넣는다.
- 4a: 보드에 로컬 브로커(mosquitto)를 띄우고 30초 껐다 켜기를 3번 했다. 3번 모두 4.8초 만에 다시 저장됐다.
- 4b: 운영 수집기의 1883 연결만 2분 막았다. 막힌 지 56초 뒤에 끊김을 알아챘고, 해제 10.7초 뒤 다시 연결했고, 20.8초 뒤 첫 행이 저장됐다.
- 첫 실행은 실패했다. 보드 커널에 iptables `owner` 기능이 없어서 nft `meta skuid`로 바꿔 다시 했다.

## 왜 이렇게 했나

- 계정별 차단을 쓴 이유: 보드 하나에서 팀원 수집기 두 개가 같이 돈다. 1883 전체를 막으면 남의 수집까지 끊긴다.
- 시험 전용 nft 테이블을 쓴 이유: 끝날 때 테이블을 지우면 규칙도 같이 지워진다. 규칙이 남아 운영 수집이 계속 끊기는 사고를 막는다(DB로 치면 임시 테이블 DROP).
- `trap cleanup EXIT`을 쓴 이유: Ctrl+C나 오류로 멈춰도 정리 코드가 반드시 돈다. 실제로 첫 실행이 중간에 실패했을 때도 남은 규칙이 없었다(Java의 `finally`).

## 말로 설명할 수 있어야 할 것 3개

1. **keepalive로 끊김을 아는 방법**: 30초마다 "살아 있니?"(PINGREQ)를 보내고 답이 없으면 끊는다. drop은 아무 응답도 없어서 바로 알 수 없고, 약 1.5배인 45~60초 뒤에 안다. 이번에는 56초였다.
2. **재연결 간격(백오프)**: 실패할 때마다 1초에서 10초까지 기다리는 시간을 늘려 가며 다시 시도한다. 브로커가 살아났을 때 모든 클라이언트가 한꺼번에 몰리지 않게 한다(DB 커넥션 풀의 재시도 백오프와 같다).
3. **지속 세션이 있어도 메시지가 빠진 이유**: 브로커는 "보낸 쪽 QoS와 받는 쪽 QoS 중 낮은 쪽"으로 전달한다. 발행이 QoS 0이면 오프라인 세션용으로 쌓아 두지 않는다(추정). 그래서 2분 동안 센서마다 2~4건이 빠졌다. Kafka처럼 디스크에 남는 큐가 아니고, 우편함이 없는 집에 배달하다가 그냥 돌아가는 것에 가깝다.
