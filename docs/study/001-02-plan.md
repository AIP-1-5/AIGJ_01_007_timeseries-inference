# 학습 노트: 과제 1 plan (데이터 수집 체계)

날짜: 2026-10-21 · 문서: [plan.md](../../specs/001-data-collection/plan.md), [research.md](../../specs/001-data-collection/research.md), [data-model.md](../../specs/001-data-collection/data-model.md) · 결정 목록: [decisions.md](../decisions.md)

## 처음 나온 용어

| 용어 | 비유 | 쉬운 정의 | 백엔드 대응 |
|---|---|---|---|
| SQLite | 엑셀 파일 하나짜리 DB | 서버 없이 파일 하나로 동작하는 SQL DB | H2 파일 모드 |
| WAL | 원장 대신 메모장에 먼저 적고 나중에 옮김 | 변경을 별도 로그 파일에 먼저 쓰는 방식. 읽는 사람은 원장을 보고 쓰는 사람은 메모장에 써서 서로 안 막는다 | PostgreSQL WAL, MVCC 읽기 |
| `INSERT OR IGNORE` | 이미 있는 번호표면 조용히 무시 | 기본키가 겹치면 에러 없이 건너뛰는 INSERT | MySQL `INSERT IGNORE`, `ON CONFLICT DO NOTHING` |
| epoch(구간 번호) | 번호표 묶음 번호 | 재가입마다 1씩 올려 "몇 번째 번호표 묶음인지" 표시. fCnt가 리셋돼도 키가 안 겹친다 | 시퀀스 리셋 시 세대(generation) 컬럼 |
| QoS 1 | 등기우편: 최소 한 번은 배달 | 브로커가 받았다는 확인을 받을 때까지 다시 보낸다. 중복은 생길 수 있다 | at-least-once 전달 |
| `clean_session=False` | 부재중 우편 보관 신청 | 같은 client id로 다시 붙으면 브로커가 끊긴 동안의 메시지를 줄 수 있다 | Kafka consumer group의 커밋된 offset |
| systemd 유닛 | 건물 관리인에게 맡긴 "꺼지면 다시 켜기" 지시서 | 리눅스 서비스 관리 설정 파일. 부팅 시 시작, 죽으면 재시작 | Spring Boot를 서비스로 등록, k8s `restartPolicy: Always` |
| heartbeat | 경비원 순찰 도장 | 60초마다 "살아 있음"을 DB에 기록. 도장이 빠진 시간 = 꺼져 있던 시간 | 헬스체크 로그 |
| TOML | 섹션이 있는 `.properties` | 사람이 읽기 쉬운 설정 파일 형식. 파이썬 3.11+에 읽기 모듈 기본 포함 | `application.yml` |

## 무엇을 했나

- 데이터 30건과 InfluxDB 구조를 보고 결정 10개(R1~R10)를 근거와 함께 정했다. 정리는 [decisions.md](../decisions.md).
- 테이블 4개를 설계했다: `readings`(측정값), `devices`(센서별 epoch 상태), `collector_events`(시작·끊김·heartbeat), `rejected`(버린 메시지).
- 구조: MQTT 콜백 → 큐 → 쓰기 스레드 1개 → SQLite. systemd로 상시 실행.
- 구현 전에 남은 질문 3개를 사용자에게 받았다: join 구독(승인), 긴 간격 센서 판정(10/22까지 세 지표 모두 보고), DB 위치(`~/data/tsinfer/`).

## 왜 이렇게 했나

- **SQLite + WAL**: 분당 15건이라 서버형 DB는 과하다. 보드 메모리 8GB를 LLM과 나눠 쓰므로 가벼워야 한다. WAL이면 과제 2 분석이 읽는 동안에도 수집이 멈추지 않는다.
- **큐로 수신과 저장 분리**: DB가 잠깐 느려져도 MQTT 루프가 막히면 keepalive가 밀려 연결이 끊긴다. 큐가 완충 역할을 한다.
- **메시지 1건 = 트랜잭션 1개**: readings 삽입과 devices 상태 갱신이 함께 성공하거나 함께 실패해야 epoch이 틀어지지 않는다(FR-008).
- **설정 파일로 키 매핑**: 센서 메시지 형식이 바뀌어도 코드를 고치지 않는다(원칙 VI, 산출물 D-2).

## 짚어 둘 것 (트랜잭션·동시성·인덱스·병목)

- **롤백**: 메시지 저장 중 예외가 나면 그 메시지의 모든 행과 devices 갱신이 함께 취소된다. 스레드는 죽지 않고 다음 메시지로 간다.
- **동시성**: DB에 쓰는 것은 쓰기 스레드 하나뿐이다. 그래서 epoch 판정(읽고-고치고-쓰기)에 경쟁 조건이 없다. 이벤트(연결 끊김 등)도 큐를 거쳐 같은 스레드가 쓴다.
- **인덱스**: `(location, item, measured_at)`는 커버율 조회용이다. 쓰기마다 인덱스 2개 + PK를 갱신하지만 분당 70행이라 부담이 없다.
- **데이터가 늘면**: 1년 약 5GB. 병목은 쓰기가 아니라 긴 읽기다. 오래 열린 읽기 트랜잭션이 WAL 파일을 키운다. 그래서 분석은 짧은 쿼리나 내보낸 사본으로 한다(추정: 1년치 전체 스캔은 수십 초, 확인 필요).

## 말로 설명할 수 있어야 할 것 3개

1. WAL 모드에서 읽기가 쓰기를 막지 않는 이유와 남는 위험(긴 읽기 → WAL 파일 증가).
2. epoch을 올리는 세 조건(0 근처, 크게 줄어듦, 측정 시각이 더 늦음)이 각각 어떤 오판을 막는지.
3. 브로커가 꺼졌다 켜졌을 때 수집기가 다시 붙는 과정(재연결 1~10초 간격 → `on_connect` → 재구독)과 그것이 60초 안에 들어오는 이유.

## 스스로 확인할 질문 2개

1. 큐가 가득 차면 무슨 일이 생기고, 그 사실은 어디에 기록되는가?
2. 수집기가 `kill -9`로 죽어 `stop` 이벤트가 없을 때, 꺼져 있던 시간을 어떻게 알아내는가?
