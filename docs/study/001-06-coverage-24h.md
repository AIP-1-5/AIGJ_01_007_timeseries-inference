# 과제 1 24시간 결과에서 배운 것

결과: [coverage-2026-10-22.md](../reports/001-data-collection/coverage-2026-10-22.md) · 판정표: [001-data-collection/README.md](../reports/001-data-collection/README.md)

## 무엇을 했나

10-21 16:04 ~ 10-22 16:04 KST 24시간의 수집 현황 보고서를 `collector report`로 만들고, 빠진 구간마다 원인을 확인해 해석을 썼다. 판정 항목 11개가 모두 95%를 넘었다. 1분 칸 기준 98.3~98.8%, 회의실은 간격 기준 98.6%다. 계획에 없던 재부팅 2번이 "재부팅 후 자동 재개"의 증거가 됐다.

## 왜 이렇게 했나

- **빠진 시간을 원인별로 나눴다.** 숫자 98%만 보면 "수집기가 2% 놓쳤다"로 읽힌다. 실제로 수집기 자신의 오류(쓰기·파싱·큐 버림)는 0건이었다. 빠진 시간은 보드 멈춤 2번, 의도한 시험 1번, 센서 무선 손실이었다. 원인을 나눠야 무엇을 고칠지 정해진다.
- **의도한 중단을 숨기지 않았다.** 과제 8 시험으로 수집기를 10분 멈춘 것도 측정 구간 안이라 그대로 보고서에 남기고 "의도한 중단"으로 표시했다. 빼고 계산하면 숫자는 좋아지지만 근거가 흐려진다.
- **회의실 경계 구간을 확인했다.** "원인 미상" 6분은 측정 끝 시각(16:04)이 10분 간격 센서의 두 메시지 사이에 걸린 것이었다. fCnt가 이어져 손실이 아니다.

## 짚어 둘 것 (동시성·병목)

- 수집 DB는 WAL이라 추론 서비스가 매분 읽어도 쓰기가 밀리지 않았다(쓰기 오류 0). **저장소 잠금은 문제가 아니었다.**
- 병목은 **같은 보드의 메모리**였다. 학습과 TensorRT 빌드가 메모리를 다 쓰자 수집기·서비스·팀원 수집기가 함께 멈췄다. 백엔드로 치면 DB 커넥션은 넉넉한데, 같은 서버의 배치 작업이 메모리를 다 먹어 API 서버까지 죽은 상황이다.

## 내가 말로 설명할 수 있어야 할 것 3개

1. 회의실 1분 커버율 10%가 왜 "통과"인지 (센서 간격 기준 커버율, fCnt 건너뜀으로 진짜 손실을 구분).
2. 빠진 구간 원인 4종류를 무엇으로 구분했는지 (heartbeat 공백, stop/start 이벤트, fCnt 건너뜀, 앞뒤 데이터).
3. 저장소를 나눠도 보드가 멈춘 이유와, 그래서 학습을 맥으로 옮긴 이유.

## 스스로 확인할 질문 2개

1. 같은 센서·같은 fCnt가 두 번 오는 중복(약 4%)을 막지 않았다면, 이 보고서의 어떤 숫자가 틀어졌을까?
2. 보드가 멈춘 18:49~18:57 동안 센서가 보낸 메시지는 영원히 사라졌을까? (힌트: QoS 1 + 지속 세션, 브로커가 얼마나 보관하나)
