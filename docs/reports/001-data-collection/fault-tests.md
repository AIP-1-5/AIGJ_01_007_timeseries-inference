## AC-1 브로커 껐다 켜기 (T029)

**측정 조건**: 보드 B(`team5-b`), 전원 모드 MAXN_SUPER, 2026-10-23 09:22~09:32 KST, 커밋 `59012c6`(시험 스크립트는 그 위 작업 트리), 사용자가 `bash deploy/fault-test-t029.sh` 실행. 원자료 `~/data/tsinfer/fault-test-20261023-092255.txt`(4a), `fault-test-20261023-092938.txt`(4b). 수집기 설정 `keepalive_s=30`, `reconnect_min_s=1`, `reconnect_max_s=10`.

- 4a: 로컬 mosquitto 2.0.18을 30초 정지 → 시작, 3회. 시험용 수집기(`test-local.db`)와 5초마다 발행하는 가짜 센서(QoS 1).

|---|---|
| 00:29:38 | 차단 시작 |

| 00:31:59.5 | 첫 새 행 (센서가 다음 메시지를 보낸 시각) |

**해석**

- 4a의 4.8초는 거의 전부 "다음 가짜 센서 메시지까지 기다린 시간"이다(5초 간격). 재연결 자체는 1초 안팎이다(최소 재시도 1초).
- 4b의 20.8초 = 재시도 대기(해제 직전 시도가 00:31:39에 실패 → 10초 뒤 재시도) 10.7초 + 다음 센서 메시지까지 10초. 최악은 재시도 최대 10초 + 연결 시간 초과 + 센서 간격 60초라서 **실센서 기준으로는 60초를 넘을 수 있다**(추정). 판정 문구 "1분 안에 수집이 다시 시작된다"를 "1분 안에 다시 연결·구독된다"로 읽으면 여유가 있다(10.7초).
- **새로 안 사실: 끊긴 동안의 메시지는 돌아오지 않았다.** 지속 세션(`session_present=True`)으로 다시 붙었지만 00:30~00:31 측정분이 저장되지 않았다. 1분 간격 센서마다 fCnt가 2~4 건너뛰었다(예: `9818` 106288 → 106291). 원인은 ChirpStack이 QoS 0으로 발행해서 브로커가 오프라인 세션용으로 쌓아 두지 않는 것으로 보인다(구독 QoS 1이어도 실제 전달 QoS는 둘 중 낮은 쪽, 추정. 브로커 설정은 우리가 볼 수 없어 확인 필요).
- 그래서 T028(강제 종료)의 "손실 0"도 다시 봤다. 9초 공백에 보낼 차례인 메시지가 없었을 뿐, 늦게 도착한 행은 0건이었다(모든 행이 측정 0.23초 뒤 수신). "브로커가 보관했다가 넘겨줬다"는 설명은 근거가 없어 고쳤다.
- 이 손실은 커버율 보고서가 `연결 끊김`으로 분류하는 결측이다. 짧은 끊김을 메우려면 InfluxDB `iot-bucket`에서 같은 구간을 되채우는 방법이 있다(구현하지 않음).
- 4b로 운영 DB에 생긴 2분 결측은 의도한 중단이다.
