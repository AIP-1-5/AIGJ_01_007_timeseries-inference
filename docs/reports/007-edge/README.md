p95가 평균보다 작은 칸은 분포가 한쪽으로 긴 경우다. 대부분 빠르고 몇 번만 크게 느렸다.

## TensorRT FP16을 못 잰 이유

1. 1차(18:47): TensorRT 11에는 `BuilderFlag.FP16`이 없다. 정밀도를 네트워크 타입으로 정하는 방식으로 바뀌었다. → 오류를 기록하고 나머지 방식만 측정을 끝냈다(위 표).
2. 2차(18:49): ONNX를 FP16으로 바꿔 strongly typed 네트워크로 빌드하도록 고쳐 다시 돌렸다. **같은 분에 보드 메모리가 98%(7,375/7,485MB)까지 찼고 18:55에 보드가 재부팅됐다.** 1차 최대 사용량은 5,420MB였다. 엔진 빌드가 작업 메모리를 크게 잡은 것이 원인으로 보인다(추정).
3. 대응: 빌드 작업 메모리 상한 256MB(`TRT_WORKSPACE_MB`)를 넣었다. 남은 메모리가 3,000MB보다 적으면 `tsmodel edge`가 시작하지 않는다. 다시 잴 때는 팀에 알리고 보드가 한가할 때 한다.

## 결론

- **서비스 추론은 ONNX Runtime CPU로 바꾸는 것을 추천한다.** 지금 서비스(과제 8)는 PyTorch CPU다. ONNX Runtime은 세 모델 모두 0.15ms 이하이고 원래 결과와 같다(CO₂ 0.0003ppm). 서비스 주기(815ms) 대부분은 모델이 아니라 DB 읽기와 전처리다(과제 8).
- PyTorch CPU가 ONNX Runtime보다 GRU에서 **400배** 느렸다. 모델 계산보다 PyTorch 연산 호출 비용이 크기 때문이다. 이렇게 작은 모델에서는 계산량보다 프레임워크 오버헤드가 지연을 정한다.
- GPU는 0.5~0.9ms로 오히려 ONNX Runtime CPU보다 느렸다. CPU → GPU 복사와 커널 실행 준비 비용이 계산보다 크다. GPU 사용률도 평균 0.9%였다.

## 생각해 볼 점에 대한 답

- **CPU로 1ms면 충분한데 왜 변환하나?** 보드 하나에 다른 모델(다음 주 로컬 LLM, 임베딩)이 같이 올라간다. 공간이 4개에서 수십 개로 늘면 지연과 메모리가 공간 수만큼 늘어난다. 같은 일을 적은 CPU 시간·전력으로 하면 그만큼 다른 모델에 남는다. 이번 결과로는 **변환(ONNX Runtime)만으로 CPU 시간이 1/400**이 됐다.
- **GRU와 TCN 중 무엇이 변환 후 더 빨라지나?** TCN(합성곱)일 것으로 추정한다. GRU는 시점을 하나씩 순서대로 계산해야 해 병렬화가 어렵다. 합성곱은 모든 시점을 한 번에 계산해 GPU·TensorRT가 잘 묶는다. 직접 재지는 않았다.
- **평균보다 p95가 중요한 이유**: 서비스는 매분 정해진 시각에 끝나야 한다. 평균이 빨라도 가끔 느린 한 번이 주기를 넘기면 그 분의 결과가 빠진다. 백엔드의 API 응답 시간 SLA를 평균이 아니라 p95·p99로 거는 것과 같다.
