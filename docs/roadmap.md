## 공부 방식 (팀장 루프)

나는 팀장, Claude는 팀원이다. 과제를 끝내는 것보다 내가 이해하는 것이 목적이다 (강사 지침).

1. 과제를 시작하면 Claude는 답을 주기 전에 "생각해 볼 점"에 대한 **내 가설**을 먼저 묻는다.
2. spec 검토: 확인 기준 숫자가 그대로 있나, 지시하지 않은 기능이 끼었나, 설계 이유를 내가 설명할 수 있나.
3. plan에서 모르는 용어만 뽑아 비유 → 쉬운 정의 → 이 과제에서의 역할 순으로 설명한다.
4. 구현 후 내가 직접 재현할 명령 1개, 일부러 고장 내 볼 것 1개를 제시한다.
5. 결과와 내 가설을 비교하고, 틀린 이유를 학습 노트에 남긴다.
6. 단계마다 `docs/study/`에 학습 노트(하루 문서 `daily/`, 과제 문서 `assignment-0N.md`), 결정은 `docs/decisions.md`에 기록한다.

**시각과 중복**
- 게이트웨이 `...dccc`의 시계가 약 4분 56초 빠르고, uplink의 `time` 필드가 그 시계를 따른다.

- 같은 센서·같은 fCnt가 게이트웨이 조합만 달리 두 번 발행된다 (샘플 30건 중 2건). `nsTime`과 `deduplicationId`가 서로 달라 둘 다 중복 판단에 못 쓴다.
- InfluxDB `iot-bucket`의 `_time`은 5분 오차가 없다 (nsTime 기준과 일치 확인).

**InfluxDB 구조** (`iot-bucket`): measurement = 항목 이름(co2, temperature, LAeq ...), field = `value`, tag = `device_id`, `location`, `point`, `spot`. 교육장 내부망이라 보드 B에서만 접속된다.

**끊긴 동안의 메시지 (2026-10-23, T029)**: 수집기가 끊겼다 다시 붙으면 `session_present=True`인데도 끊긴 동안의 메시지가 오지 않는다(2분 차단에 센서마다 2~4건 손실). 발행이 QoS 0인 것으로 보인다(추정). 결측은 InfluxDB에서 되채울 수 있다. 보드 커널에 iptables `owner` 매치가 없어 계정별 차단은 nft `meta skuid`로 한다.

**기타 topic**: `tsinfer/<사람>/<공간>`은 다른 사람의 예측 서비스 결과로, 과제 8 결과 형식의 참고 예시. `xflow/hvacr/...`는 냉난방기 상태(과제 4 참고 가능).

## 과제 1 내 가설 노트

- 요약: 학습에 쓸 데이터가 끊기지 않도록, MQTT 센서 값을 받아 저장하고, 형식이 바뀌어도 설정만 바꿔 대응하며, 끊기면 사람 손 없이 복구되고, 현황을 한눈에 볼 수 있는 수집기.
- 시각: 센서에 시계가 없으므로 네트워크 서버 시각(nsTime)을 쓴다. 게이트웨이 시각은 dccc 오차, 수집기 수신 시각은 지연 시 몰림 때문에 쓰지 않는다. 둘 다 별도 저장해 원인 설명에 쓴다.
- 저장소 공유: 같은 저장소면 잠금 경합으로 수집이 밀리고, 데이터가 계속 바뀌어 재현성이 깨진다. 수집 DB는 수집 전용, 학습은 기간을 고정한 스냅샷. 같은 보드라 메모리 경쟁은 남으므로 무거운 학습 전 팀 공지.
