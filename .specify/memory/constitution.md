# 시계열 데이터 추론 실습 Constitution

이 문서는 과제 진행 중 모든 spec·plan·tasks·구현이 지켜야 하는 원칙이다.
과제의 원문은 팀 Private 저장소 `AIP-1-5/docs`의 `assignment.md`(보통 `../docs/assignment.md`)이고, 원칙은 그 문서의 확인 기준과 평가 기준(§5)에서 나왔다.

## Core Principles

### I. 확인 기준이 곧 완료 조건

- 과제 하나를 spec 하나로 다룬다. 한 spec에 여러 과제를 섞지 않는다.
- 각 spec은 `assignment.md`에 있는 해당 과제의 "확인 기준"을 빠짐없이 완료 조건(acceptance
  criteria)으로 옮긴다. 수치 기준(예: 커버율 95%, 기준선 대비 30%)은 숫자 그대로 적는다.
- 확인 기준을 하나라도 충족하지 못하면 그 과제는 완료가 아니다. 미충족이면 숫자와 원인을 함께 기록한다.
- 각 spec은 해당 과제의 "산출물"을 tasks에 포함한다.

근거: 성능 영역(25%)은 과제별 확인 기준 충족 여부로 평가된다.

### II. 공정한 평가와 누수 금지 (NON-NEGOTIABLE)

- 학습·검증·시험 기간은 시간 순서로 나눈다. 무작위로 섞지 않는다.
- 정규화 값(평균·표준편차 등)과 모든 학습된 전처리 파라미터는 학습 기간 데이터로만 계산한다.
- 시험 기간 데이터는 학습, 하이퍼파라미터 선택, 임계값 결정, 모델 선택에 쓰지 않는다.
  선택은 검증 기간으로 한다.
- 기준선과 모든 모델은 같은 시점, 같은 조건, 같은 지표로 비교한다.
- 정답을 만든 정보를 입력에 넣지 않는다(예: 일정으로 만든 사용 여부 정답에 일정을 입력으로 쓰지 않는다).

근거: 공정한 평가 영역(10%)에서 시험 데이터를 학습·선택에 쓰면 미흡이고, 누수가 있는 숫자는
다른 모든 결과를 무의미하게 만든다.

### III. 전처리는 한 곳에서

- 정제·결측 처리·리샘플링·정규화·특성 생성은 하나의 공용 모듈에 둔다.
- 학습, 평가, 상시 서비스는 모두 이 모듈을 호출한다. 전처리 코드를 복사해 따로 고치지 않는다.
- 학습 때 계산한 전처리 파라미터는 모델 파일과 함께 저장하고, 서비스는 그것을 불러 쓴다.

근거: 과제 8은 "학습 때와 똑같은 전처리"를 요구한다. 전처리가 갈라지면 오류가 조용히 생긴다.

### IV. 측정 조건을 기록한다

- 모든 결과표와 그래프에는 데이터 기간, 실데이터/합성 여부, 시험 기간, 보드 전력 모드를 함께 적는다.
- 지연·메모리·전력 측정에는 전력 모드, 클럭 고정 여부, 반복 횟수, 워밍업 횟수, 배치 크기를 추가로 적는다.
- 결과는 다시 만들 수 있어야 한다. 실행한 명령, 설정 파일, 난수 시드, 코드 커밋을 남긴다.

근거: README §4가 모든 결과표에 측정 조건을 요구하고, 과제 7 확인 기준에 포함되어 있다.

### V. 결과에는 해석이 따라온다

- 결과마다 "왜 이렇게 나왔는가"와 "그래서 무엇을 해야 하는가"를 쓴다. 숫자만 나열하지 않는다.
- 모델이 못하는 것(못 잡는 고장 종류, 안 맞는 공간, 틀리는 시간대)을 구체적으로 짚는다.
- 각 과제의 "생각해 볼 점"에 답한다.

근거: 해석 영역이 30%로 가장 크다.

### VI. 사람 손 없이 복구된다

- 상시 프로세스(수집기, 추론 서비스)는 systemd 서비스로 운영하고, 실패 시 자동 재시작한다.
- 브로커 재시작, 네트워크 끊김, 보드 재부팅 뒤 사람 개입 없이 다시 동작한다.
- 한 주기의 실패가 다음 주기를 막지 않는다. 데이터 끊김 같은 상태는 숨기지 않고 출력으로 알린다.
- 메시지 형식 변경이나 센서 추가는 코드 수정이 아니라 설정 변경으로 대응한다.

근거: 동작 영역(25%)은 장애 시험 통과 여부로 평가된다(과제 1, 8).

### VII. 단순한 것부터

- 제공 키트가 있으면 먼저 그대로 실행해 결과를 확인한 뒤 바꾼다.
- 기준선을 먼저 재고, 기준선을 이기지 못하면 더 복잡한 모델을 추가하지 않는다. 원인부터 찾는다.
- 복잡도를 더할 때는 plan에 이유를 적는다.

근거: README 과제 2가 강조하듯 단순한 방법이 생각보다 강하고, 기준선을 못 넘으면 성능 영역 미흡이다.

## 운영 제약 (Jetson 환경)

- 장비: Jetson Orin Nano Super Developer Kit (8GB, CPU·GPU 메모리 공유), JetPack 7.2.1, Ubuntu 24.04, NVMe SSD.
- 보드 A는 운영 전용이다(수집기와 제출 서비스, 24시간). 보드 A에서 실험·재부팅을 하지 않는다.
  보드 A는 GitHub에서 pull해서 배포만 한다.
- 보드 B는 실험·학습·측정용이다. 무거운 모델을 돌리기 전에 팀에 알린다.
- 같은 보드 위에서 로컬 LLM·임베딩 모델과 함께 돌아야 하므로 메모리 사용량을 측정하고 plan에 예산을 적는다.
- TensorRT 엔진(`.engine`)은 실행할 보드에서 빌드한다. 다른 TensorRT 버전에서 만든 엔진을 옮겨 쓰지 않는다.
- 비밀값(MQTT 계정, DB 토큰)은 `.env`에만 두고 커밋하지 않는다. 코드·문서·로그에 적지 않는다.
- 큰 파일(DB, 원시·가공 데이터, `.pt` `.onnx` `.engine`)은 GitHub에 올리지 않는다. 보드의 `/srv/team5`에 둔다.
- `sudo apt autoremove`를 쓰지 않는다. 전원은 `sudo poweroff` 후에 뽑는다.

## 개발 흐름

1. 과제는 한 번에 하나씩, 번호 순서대로 진행한다. spec 번호는 과제 번호와 맞춘다
   (예: 과제 1 → `001-data-collection`).
2. `/speckit-specify` → (필요하면 `/speckit-clarify`) → `/speckit-plan` → `/speckit-tasks`까지 진행한 뒤
   멈추고 사용자가 검토한다. 사용자가 승인하기 전에는 `/speckit-implement`를 실행하지 않는다.
3. 구현 후 `/speckit-converge`로 확인 기준 충족 여부를 점검하고, 충족할 때까지 반복한다.
4. 과제 산출물(보고서, 표, 그래프)은 `docs/reports/`에 과제 번호별로 남긴다.
5. 커밋 전에 비밀값과 큰 파일이 포함되지 않았는지 확인한다.

## Governance

- 이 constitution은 spec·plan·tasks·구현 전반에서 다른 관행보다 우선한다.
  plan의 Constitution Check는 위 원칙 I~VII과 운영 제약을 기준으로 한다.
- 원칙과 충돌하는 결정이 필요하면 plan에 이유와 대안을 적고 사용자 승인을 받는다.
- 개정은 사용자가 승인한 뒤 이 파일을 고치고 버전을 올린다. 원칙을 빼거나 뜻을 바꾸면 MAJOR,
  원칙·섹션을 추가하거나 크게 넓히면 MINOR, 문구 수정은 PATCH.
- 작업 중 참고할 실행 정보(보드 접속, 폴더, 명령)는 `CLAUDE.md`에 둔다.
