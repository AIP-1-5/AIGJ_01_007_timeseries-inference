# /day-end

오늘 작업을 마무리한다. **커밋은 내가 diff를 보고 승인한 뒤에만 한다. push는 하지 않는다.**

## 1. 오늘 한 일 모으기

- 오늘 날짜: `date '+%Y-%m-%d %a'`
- `git log --since=midnight --stat --format='%h %s'`, `git status --short`, `git diff --stat`
- 진행 중인 spec(`specs/` 아래 가장 번호가 큰 폴더)의 `tasks.md`에서 오늘 체크된 작업.
  실제로 끝났는지(테스트 통과, 파일 존재) 확인하고, 안 끝난 것은 체크하지 않는다.
- 이 대화에서 새로 알게 된 사실(데이터 특성, 미팅·강사 답변, 마감일)과 실제로 겪은 문제(실패한 테스트, 오류 메시지, 잘못 짚은 가정).

## 2. `docs/roadmap.md` 고치기

파일이 없으면 만들지 말고 "roadmap.md가 없다, 새로 만들까?"를 추천안과 함께 묻는다.

1. **현재 위치**: 끝난 단계(spec, plan, tasks, 구현, 보고서)의 체크박스를 갱신한다.
2. **과제가 끝났으면**: 다음 과제의 날짜별 계획을 "현재 위치"에 추가한다.
   앞 과제 결과, 마감일, 하루 5시간, 주말 휴식을 반영한다.
3. **새로 알게 된 사실**: 해당 섹션에 반영한다.
4. **일정이 밀렸으면**: 무엇을 줄일지(심화 B 제외, 범위 축소) 추천안을 같이 쓴다.
   형식: 추천안 + 이유 1줄 + 버리는 것 1줄.
5. **변경 기록**: 파일 맨 아래 "변경 기록"에 `- YYYY-MM-DD: 한 줄 요약`을 추가한다.

## 3. 학습 문서 (`docs/study/`)

### 개념 정리 형식 (두 문서 공통)

개념마다 네 줄:

```markdown
### <개념 이름>
- 정의: <한 줄>
- 비유: <일상 비유 한 줄. 백엔드 개념(DB, 트랜잭션, 큐, 인덱스)에 대응되면 함께 쓴다>
- 이 레포에서는: `<파일>:<라인>` — <거기서 무엇을 하는지>
- 잘못하면: <틀리게 쓰면 실제로 생기는 일>
```

`파일:라인`은 지금 커밋 기준으로 실제 파일을 열어 확인한 위치만 쓴다.

### 3-1. 하루 문서: `docs/study/daily/YYYY-MM-DD.md` (매일)

이미 있으면 덧붙인다. 구성:

1. **오늘 한 일** — 5줄 요약
2. **오늘 처음 나온 개념** — 위 형식. 이전 하루 문서·과제 문서에 이미 나온 개념은 빼고 링크만 건다
3. **실제로 겪은 문제 → 원인 → 해결** — 오늘 대화와 git 기록에 실제로 있었던 것만. **지어내지 않는다.** 없으면 "없음"
4. **직접 쳐 볼 명령 3개와 예상 결과** — sudo 없이 내 계정으로 안전하게 칠 수 있는 명령. 명령 → 예상 결과 → 다르면 의심할 것
5. **아직 모르는 것** — 답을 못 찾은 질문, "추정"으로 남긴 내용

### 3-1b. 단계 노트 (전역 규칙)

오늘 spec, plan, tasks, 구현 중 끝난 단계가 있는데 `docs/study/<spec번호>-NN-<단계>.md`(예: `001-03-tasks.md`)가 없으면 쓴다:
무엇을 했나 / 왜 이렇게 했나 / 말로 설명할 수 있어야 할 것 3개 / 스스로 확인할 질문 2개.
코드·설계 노트에는 롤백, 동시성, 인덱스 영향, 데이터가 늘었을 때의 병목을 짚는다.

### 3-2. 과제 문서: `docs/study/assignment-0N.md` (과제 하나가 끝났을 때만)

과제 완료 판단: 해당 spec의 확인 기준 판정표(`docs/reports/<spec>/README.md`)가 있고 tasks.md가 모두 체크됨. 아니면 쓰지 않는다. 구성:

1. **한 장 요약** — 무엇을 왜 만들었고 결과가 어땠는지
2. **흐름도 (Mermaid) 1~2장** — 데이터 흐름, 장애 복구 흐름 등. ` ```mermaid ` 블록으로
3. **핵심 개념 정리** — 위 형식. 하루 문서의 개념을 모아 정리한다
4. **결정과 이유** — `docs/decisions.md`의 해당 과제 결정 요약(결정 / 이유 / 버린 대안)
5. **확인 기준 결과표** — `기준 | 숫자 | 통과 여부 | 원인` (미통과면 원인 필수). 숫자는 보고서에서 그대로 가져온다
6. **"생각해 볼 점": 내 처음 가설 vs 실제 결과** — 가설은 spec·plan·research에 적힌 것에서 가져오고, 실제 결과는 보고서 숫자로
7. **강사 질의응답 예상 질문 5개** — 질문마다 3줄 답변
8. **다음 과제로 넘길 것** — 데이터 특성, 남은 문제, 재사용할 코드

### 공개 저장소 규칙 (두 문서 모두)

이 저장소는 Public이다. 쓰기 전과 커밋 전에 확인한다.

- 비밀값(MQTT 주소·계정·비밀번호, InfluxDB 토큰·조직 ID)을 쓰지 않는다.
- 센서·게이트웨이 **전체 ID를 쓰지 않는다**. 필요하면 공간·모델 이름(예: "회의실 AM103")이나 끝 4자리(`…9152`)로 쓴다.
- 사람 이름(팀원, 강사)을 쓰지 않는다. "팀원", "강사"로 쓴다.
- 점검: `grep -nE '[0-9a-f]{16}' docs/study/` 결과가 비어 있어야 한다.

## 4. 커밋 전 점검과 승인

1. 커밋할 파일 목록과 `git diff`(roadmap.md는 전체 diff, 나머지는 `--stat` + 핵심 부분)를 보여 준다.
2. 점검: `.env`, `*.db`, 원본 데이터(`uplink_raw.jsonl` 등), 비밀값, 모델 파일이 없는지, `docs/study/`에 전체 ID·사람 이름이 없는지 확인하고 결과를 한 줄로 쓴다.
3. 커밋 메시지 안을 보여 주고 **승인을 기다린다.** 승인 전에는 `git add`/`git commit`을 하지 않는다.
4. 승인하면 커밋하고 `git log -1 --stat`을 보여 준다. push는 하지 않고, 필요하면 명령만 보여 준다.
